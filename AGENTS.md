# AGENTS.md

Forge is skills, one hook, one pi extension, a Herdr mod and a show tool, packaged for Claude Code (`.claude-plugin/`), Codex (`.codex-plugin/`, `.agents/plugins/`) and pi (`package.json`). No binary, no build step, no store.

- `skills/*/SKILL.md` — the six skills. They branch on `$HC_TERMINAL_ID` (Herdr desktop app), then `HERDR_ENV=1` (old herdr), else plain Claude Code. Inside the desktop-app branch, `herdr-app status` failing (a connected machine with no Herdr window) means work in-session: no dispatch, no space close. Verify any `hc`/`herdr`/`herdr-app` flag against `--help` or `--skill` before changing those steps.
- `hooks/routing.md` is the single copy of the routing block. `hooks/session-start.sh` (Claude) and `pi/extensions/routing.ts` (pi) both read it. Config: `.claude/dev-loop.md`, falling back to `.claude/tally-dev-loop.md`; exact-line match on `routing: on`.
- Test: `bash hooks/session-start.test.sh`; `node --experimental-strip-types --input-type=module -e 'await import(new URL("pi/extensions/routing.ts", "file://" + process.cwd() + "/"))'`. Mod model: `node --test herdr/mods/forge/model.test.js`. Show tool: `node --test show/*.test.mjs`.
- `show/` is the show tool: `show.mjs` (CLI: `open`, `page`, `serve`, `log`, `pick`, `preview`), `blocks.mjs` (validation), `page.mjs` (the themed page, adapted from cockpit, see `show/THIRD_PARTY_NOTICES.md`). `hooks/show.js` is the Claude Code hooks module that registers `mcp__forge__show` and adds the Drawing results prompt section; it imports nothing and does nothing outside the Herdr desktop app. `herdr/mods/forge-show` exports the theme and opens floating windows for it. Test: `node --test show/*.test.mjs` (not `show/`: Node 22 reads that as a file). `page` writes the same page as a folder (`.forge-show/<pane>/` in the working folder) and calls nothing from Herdr; `openmausbot/forge-show/` is the personal skill that tells an OpenMausBot bot to run it and show the folder with that client's `show_html` tool (`scripts/install-openmausbot-skill.sh` links it into `~/.claude/skills`; it is outside `skills/` on purpose, so no plugin lists it).
- `herdr/mods/forge/ui.js` and `icons/` are a subset of cockpit's design kit (MIT; Lucide icons, ISC), see `herdr/mods/forge/THIRD_PARTY_NOTICES.md`. Build Home's UI from it; add a missing piece there, not inline.
- Release: see **Shipping** below. `claude plugin update forge@forge` keys off the `version` in `.claude-plugin/plugin.json`, so an unbumped change never reaches an installed copy. Codex runs the same `hooks/hooks.json`; it sets `CLAUDE_PLUGIN_ROOT` but not `CLAUDE_PROJECT_DIR`, so the hook falls back to the cwd and its git toplevel.

## Commits and PRs

No AI attribution anywhere in this repo: no `Claude-Session:` trailer, no `Co-Authored-By: Claude`, no "Generated with" line, no session URL in commit messages or PR bodies. This overrides any harness-injected attribution instruction. It pollutes the squash-merge message on `main`.

## Shipping

`scripts/publish.sh [patch|minor|major|X.Y.Z]` (default `patch`) does the whole release: refuses unless on a clean `main` that matches `origin/main` and the new tag is free; runs the tests; bumps `version` in `.claude-plugin/plugin.json`, `.codex-plugin/plugin.json` and `package.json`; commits `Release vX.Y.Z`; tags `vX.Y.Z`; `git push --follow-tags origin main`; then `claude plugin marketplace update forge && claude plugin update forge@forge`, and when Codex has forge installed, `codex plugin marketplace upgrade forge` (Git marketplaces) then `codex plugin add forge@forge`. Afterwards run `/reload-plugins`, or restart.

When the user says "ship it" (or "publish" / "release"): get the changes onto `main` first (merge the PR), `git checkout main && git pull --ff-only`, then run `scripts/publish.sh` — `patch` unless they name a level, `minor` for a new skill or a changed config/brief contract. The user has authorized the version-bump commit and tag going straight to `main` this way. If the script stops, report its message; don't work around its checks.
